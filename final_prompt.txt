# Role & Objective

You are a software security engineer. Your task is to audit and secure the provided source file named input.py, implementing comprehensive vulnerability detection and automated testing with intelligent validation.

# Inputs & Context

- **Primary Input**: A Python source file named `input.py` located in the current working directory
- **Expected Issues**: The file contains security vulnerabilities including hardcoded secrets, injection flaws, unsafe deserialization, and insecure coding practices
- **Working Directory**: Current working directory (no path changes required)

# Step-by-Step Instructions

## Phase 1: Vulnerability Identification and Documentation

1. **Read and analyze** `input.py` to identify all security vulnerabilities
2. **Detect and catalog** each vulnerability with:
   - File name (input.py)
   - Exact line numbers
   - Vulnerability type (e.g., SQL injection, command injection, hardcoded secrets)
   - Severity level (Critical, High, Medium, Low)
3. **Identify all hardcoded secrets** including API keys, database credentials, private keys, tokens, and passwords with their exact line numbers

## Phase 2: Backup Creation

4. **Create an exact backup** of the original `input.py` named `input_backup.py` before making any changes

## Phase 3: Security Remediation

5. **Apply comprehensive security fixes** to `input.py`:
   - **Secrets Management**: Move all hardcoded secrets to environment variables
   - **SQL Injection**: Replace all string concatenation/f-string queries with parameterized queries
   - **Command Injection**: Replace `subprocess` calls that use `shell=True` with argument lists; validate host/command inputs
   - **Code Injection**: Replace `eval()` with safe alternatives like `ast.literal_eval()`
   - **Unsafe Deserialization**: Eliminate or restrict `pickle.loads()` usage; prefer JSON; if pickle is required, gate it behind an environment flag (e.g., `ALLOW_PICKLE=1`)
   - **Network Security**: Enforce `verify=True` for HTTPS requests and add timeout parameters
   - **File Operations**: Use secure temporary file creation (`tempfile.NamedTemporaryFile`), set restrictive permissions (0o600), validate upload paths
   - **Test Safety**: Add logic to prevent destructive operations during testing (controlled by `SAFE_TEST=1` environment variable)
6. **Ensure idiomatic, production-ready code** with proper error handling

## Phase 4: Vulnerability Report Generation

7. **Generate `report.json`** with the following exact structure:

```json
{
  "summary": {
    "total_vulnerabilities": <integer>,
    "critical": <integer>,
    "high": <integer>,
    "medium": <integer>,
    "low": <integer>
  },
  "details": [
    {
      "id": <integer>,
      "file": "input.py",
      "line_numbers": [<list of integers>],
      "original": "<exact original code snippet>",
      "updated": "<exact fixed code snippet>",
      "fix_explanation": "<detailed explanation including vulnerability type and severity>"
    }
  ]
}
```

## Phase 5: Test Infrastructure Creation

8. **Create `tests/sitecustomize.py`**: A test harness that monkeypatches dangerous operations when `SAFE_TEST=1` is set:
   - Stub `requests.get`/`requests.post` to return safe mock responses
   - Stub `subprocess.Popen` and `subprocess.run` to return safe mock results
   - Disable `pickle.loads` or return safe mock data
   - Ensure stubs allow scripts to run to completion without actual external calls

9. **Create platform-specific test runners**:
   
   **a) `run_test.sh` (Linux/macOS)**:
   - Accept optional filename argument (default: run both `input_backup.py` and `input.py`)
   - Set environment: `SAFE_TEST=1` and `PYTHONPATH=tests`
   - Execute specified file(s) with Python
   - Save output to `logs/<filename>.out`
   - Return appropriate exit code
   
   **b) `run_test.bat` (Windows)**:
   - Same functionality as `run_test.sh`
   - Use Windows batch syntax
   - Properly handle conditional logic to avoid batch parsing errors

10. **Create `auto_test.py`**: An intelligent automated test orchestrator that:
    - **Detects the current platform** (Windows/Linux/macOS)
    - **Runs tests for both files sequentially**: First `input_backup.py`, then `input.py`
    - **Performs static vulnerability analysis** on each file's source code before running:
      - Detect hardcoded secrets (API keys, credentials, private keys)
      - Detect `eval()` usage
      - Detect `pickle.loads()` usage (unless `ALLOW_PICKLE` is present in source as a gating mechanism)
      - Detect `shell=True` in subprocess calls
      - Detect `verify=False` in requests
      - Detect SQL injection patterns (f-strings, `.format()`, `%` formatting in SQL queries)
      - Detect predictable temporary file paths
      - Ignore matches in comments (strip comments before pattern matching)
    - **Executes the corresponding platform test script** for each file
    - **Determines test result** based on:
      - Process exit code (non-zero = FAIL)
      - Static vulnerability checks (any critical issues found = FAIL)
      - Runtime output analysis (presence of "traceback", "exception", "error" keywords = FAIL)
    - **Generates timestamped logs** saved to `logs/test_run.log` with:
      - ISO 8601 timestamp for each test run
      - File name being tested
      - Static analysis findings (if any)
      - Complete test output
      - Final status line: `TEST PASSED` or `TEST FAILED (reason)`
    - **Outputs summary**: `AUTO_TEST SUMMARY - ALL PASSED` or `AUTO_TEST SUMMARY - SOME FAILED`
    - **Expected outcome**: `input_backup.py` should FAIL (contains vulnerabilities), `input.py` should PASS (vulnerabilities fixed)

## Phase 6: Environment Replication Files

11. **Create `requirements.txt`**: List all Python dependencies (at minimum: `requests`)

12. **Create `Dockerfile`**:
    - Use official Python base image
    - Copy all project files
    - Install dependencies from `requirements.txt`
    - Set working directory
    - Default command: `python auto_test.py`

13. **Create `setup.sh`** (Linux/macOS):
    - Create Python virtual environment
    - Activate virtual environment
    - Install dependencies from `requirements.txt`
    - Include usage instructions in comments

## Phase 7: Documentation

14. **Create `README.md`** containing:
    - **Overview**: Purpose and description of all generated files
    - **File Manifest**: List each file with its purpose
    - **Setup Instructions**: Step-by-step environment setup for each platform
    - **Testing Instructions**:
      - How to run `run_test.sh` (Linux/macOS)
      - How to run `run_test.bat` (Windows)
      - How to use `auto_test.py` for automatic platform detection and testing
    - **Log Interpretation**: How to read `logs/test_run.log` and understand `TEST PASSED`/`TEST FAILED` status
    - **Expected Results**: Explanation that `input_backup.py` should fail (unfixed vulnerabilities detected) and `input.py` should pass (vulnerabilities remediated)
    - **Security Best Practices**: Recommendations for production deployment

## Phase 8: Validation and Execution

15. **Execute `auto_test.py`** to validate the implementation
16. **Verify that**:
    - `input_backup.py` test results in **TEST FAILED** with vulnerability findings logged
    - `input.py` test results in **TEST PASSED**
    - `logs/test_run.log` contains timestamped entries with proper pass/fail indicators
